# 学習者目線の技術記事を書くスキル

「専門家が教える」記事ではなく、**「自分はここがわからなかった。調べたらこう理解できた」を共有する記事**を書く。
読者は過去の自分と同じところでつまずいている人。その人が「自分も同じところで悩んでいた」と感じ、読み終えて腑に落ちることをゴールにする。

## 大原則

1. **つまずきを主役にする**：「何を知っているか」ではなく「どこでわからなくなったか」を軸に構成する。
2. **経験を捏造しない**：実際のつまずき、失敗談、課金額、試した結果などは、ユーザー本人が語ったものだけを書く。わからない場合は書かずに質問する（後述の「ヒアリング」）。
3. **断定しすぎない**：調べて理解した立場なので、確認できたことと、そう理解したこと・未確認のことを区別して書く。
4. **正確さは落とさない**：親しみやすい文体にしても、技術的な内容は公式ドキュメントで裏取りする。
5. **「調べた」だけで終わらせず、必ず1つは「試した」を入れる**：公式ドキュメントの要約は、読者が公式を読めば済んでしまい、いいねを押す理由にならない。コマンド実行結果・画面・実測値・再現手順など、**この記事にしかない一次情報を最低1つ**入れる（詳細は「実測・実験を入れる」）。
6. **未確認のものを公開しない**：仮置きの体験談、裏取りできていない記述、TODO が1つでも残っている間は `published: false` のままにする。
7. **1記事1テーマ**：扱う範囲を広げすぎない（詳細は「スコープを絞る」）。
8. **たとえ話（擬似語）を必ず入れる**：抽象的な概念は、日常のもの（メニュー表、注文票、郵便、図書館など）に置き換えて理解の入口を作る（詳細は「たとえ話（擬似語）を入れる」）。

## 進め方

### 1. ヒアリング（書く前に確認する）

次を確認する。ユーザーがすでに文章や下書きを渡している場合は、そこから読み取れるものは聞き直さない。

- どこでつまずいたか（疑問・誤解していたこと）
- どう調べて、何がきっかけで腑に落ちたか
- まだわかっていないこと、試せていないこと
- 想定読者（例：Webエンジニア、初学者など）
- **実際に試せるか**：手元や無料枠で再現できる実験はあるか、すでに試した結果（コマンド出力・スクリーンショット・数値）はあるか
- **記事で「1つだけ」伝えたいこと**（スコープを絞るため。下記参照）

つまずきが不明で、本文の疑問から推測して書く場合は、**推測で入れた箇所を最後にユーザーへ明示して、本人の実体験に差し替えてもらう**。差し替えが済むまで記事は `published: false` のままにする（「公開前チェック」参照）。

## スコープを絞る

1記事に詰め込みすぎると、初学者には重く、実務者には浅くなり、どちらにも刺さらない。

- **1記事1テーマ**。目安は本文 8,000〜10,000 字以内、「わからなかったこと」は 3〜4 個まで。
- 構成を作る前に「この記事で読者が持ち帰る1つのこと」を一文で決める。それに答えない節は削る。
- 次のような場合は、記事を分割する。
  - 概念の説明と、複数サービス（AWS / GCP など）ごとの構成・設定を両方扱おうとしているとき
  - 想定読者が「初学者」と「実務者」の両方になっているとき
  - 「まだ腑に落ちていないこと」が、それ自体で1記事になる大きさのとき
- 分割したら、記事の末尾に「次の記事」として予告し、1本目だけで完結するように書く。
- 分割案はユーザーに提示して決めてもらう。勝手に削らない。

## 実測・実験を入れる

「調べた」だけの記事は公式ドキュメントの要約になり、読者にとっての得が薄い。**この記事にしかない一次情報**を、1記事に最低1つ入れる。

- 例：`curl -I` でヘッダーを確認して Miss → Hit の変化を見る、`EXPLAIN` の結果を比較する、実際に構築してハマった設定とエラー文、導入前後の数値、課金額。
- 手順（コマンド）と、**実際の出力**をセットで載せる。環境・バージョン・実施日も明記する。
- **出力や数値を作らない**。実行できるのはユーザーだけなので、こちらは「試すとよい実験」と実行コマンドを提案し、結果はユーザーに貼ってもらう。結果が手元にない間は、その節を書かずに TODO にして `published: false` のままにする。
- 試せないテーマの場合は、代わりに「公式の記述と実際の画面・出力のズレ」「ハマった点」など、本人が経験したことを書いてもらう。何も一次情報がなければ、記事化するか自体をユーザーに相談する。
- 実験で公式の説明と違う結果が出たら、それは記事の価値になるのでそのまま書く（ただし条件・再現手順を添える）。

## たとえ話（擬似語）を入れる

技術用語だけの説明は、初学者には抽象的で頭に残りにくい。**日常にあるものに置き換えた「たとえ語」**を、すべての記事に必ず入れる。例：スキーマ = 「メニュー表」、リクエスト = 「注文」、キャッシュ = 「手元に置いた作り置き」。

**入れ方**

- **1記事につき、世界観を1つに統一する**（レストラン、郵便局、図書館、役所の窓口など）。概念ごとに別のたとえを持ち出さず、同じ世界の登場人物（客・メニュー・厨房など）で複数の概念を対比できるようにする。
- **「先に結論」の節に、たとえ話を必ず入れる**。比較表の直後に「たとえるなら」の小節を置き、全体像を一度たとえで描く。
- **各節の「調べてわかったこと」でも、新しい概念が出るたびに、たとえ語に言い換える**。初出で「〇〇（たとえるなら△△）」の形にしてよい。
- **たとえ語と技術用語の対応表を載せる**（例：メニュー表 = スキーマ、注文 = クエリ）。読者が両方を結びつけられるようにする。
- 既出のたとえ語は、後の節でも同じ言葉で使い続ける。途中で言い換えない。

**気をつけること**

- **たとえは理解の補助であり、事実の根拠にしない**。技術的な主張は公式ドキュメントで裏取りし、たとえ話の中で新しい事実を断定しない。
- **たとえが当てはまらない点を、1〜2文で添える**（`:::note info` などで）。例：「実際の API では、メニューにない項目を頼むとエラーになる」。たとえを鵜呑みにした誤解を防ぐ。
- **技術的に不正確になるたとえは避ける**。例外が多い概念は、「〜に近い」「〜のようなもの」と断定を避ける。
- たとえで読者を子ども扱いしない。「簡単に言うと」などの見下す表現は使わない。
- 筆者の実体験のたとえ（「インターンで〇〇だった」など）は、本人が語ったものだけを使う。たとえ話は創作でよいが、**実体験のように書かない**。
- たとえ案は2〜3個考えて、下書きには1案を入れ、他の案と差し替えられるようにユーザーに伝える。

### 2. 構成を作る

以下の型を基本にする。内容に合わせて増減してよい。

```
タイトル：短く、読者の得が見えるもの（後述「タイトルの付け方」）
# はじめに
  - なぜ調べたか（きっかけ）
  - わからなかったことのリスト（3〜5個）
  - 立場の表明（専門家ではなく、調べた範囲での共有。誤りはご指摘ください）
# 先に結論（3行 or 比較表 ＋ たとえ話）
# わからなかったこと①〜④（3〜4個まで）
  - 何がわからなかったか（素直に）
  - 調べてどう理解したか
  - 試してみた結果（コマンド＋実際の出力など。最低1か所は必須）
  - 具体例・図・コード
# まだ腑に落ちていないこと
# まとめ（箇条書き＋最後の一言）
```

ポイント：
- 先に結論を置き、読者が全体像を持ってから詳細を読めるようにする。
- 各節の見出しは「わからなかったこと」の形にして、疑問と答えを対応させる。
- 前の節で出た概念が次の節の疑問を解く、という**つながり**を明示する（例：「①がわかると、これも説明できる」）。
- 疑問は「はじめに」で列挙し、まとめで回収する。

### タイトルの付け方

一覧では先頭30文字前後しか見えず、読者は「自分の困りごとが解決するか」で開くかを決める。

- **全角 40 文字以内**を目安にする。60文字を超える長いタイトルにしない。
- **読者の困りごと・得を、先頭に近い位置に置く**。検索されそうな語（サービス名、エラー、症状）を入れる。
- 「〇〇がわからなかったので調べて整理した」の型は、冗長になりやすいので多用しない。学習者目線のトーンは「はじめに」で出せるので、タイトルでは得を優先する。
- 良い例：
  - 「CDNのキャッシュが更新されない時の対処3つ（CloudFront / Cloud CDN）」
  - 「BigQueryで SELECT * が避けられる理由を、行指向・列指向から理解する」
- 避ける例：「〇〇が△△以上にわからなかったので、A・B・Cの構成まで調べて整理した」（長い・何がわかるか見えない）
- タイトル案は2〜3個出して、ユーザーに選んでもらう。

### 3. 書く

**文体**
- です・ます調。一人称は「自分」「筆者」。偉そうな言い回し（「〜すべき」「当然」）を避ける。
- つまずきは素直に書く。例：「正直、この説明だけでは何が違うのかピンときませんでした」「最初は〜だと思っていました」
- 理解の転換点を書く。例：「ここで〇〇とつながって、やっと腑に落ちました」
- 「簡単に」「単純に」「ご存じの通り」など、読者を置き去りにする言葉は使わない。

**わかりやすさ**
- 略語・専門用語は、初出で正式名称と**自分の言葉での言い換え**を添える。
- 抽象的な説明の直後に、小さな具体例（小さな表、数行のSQL/コード）と、**たとえ話（擬似語）**を置く。
- 比較は表にする。流れや構成は mermaid 図にする（Qiita は mermaid 対応）。
- 1つの節で扱う概念は1つ。長くなる場合は節を分ける。
- 「意外だったこと」「誤解しやすいこと」は `:::note info` / `:::note warn` で目立たせる。

**正確さ**
- 「必ず」「常に」「できない」の断定を疑う。例外・条件がある場合は書き添える。
- 製品・サービスの仕様、料金、制限は変わりうるので、公式ドキュメントを確認し、前提（課金モデル、バージョンなど）を明記する。
- 確認できていないことは「〜と理解しています」「〜のようです」とし、裏取りできていない内容を事実として書かない。

### 4. セルフチェック

仕上げる前に確認する。

- [ ] 「はじめに」で挙げた疑問は、すべて本文で答えが出ているか
- [ ] つまずきの記述は、ユーザー本人の実体験か（捏造していないか）
- [ ] 初出の用語に言い換えがあるか
- [ ] 断定表現に、例外・前提が添えられているか
- [ ] 「まだわかっていないこと」を正直に書いているか
- [ ] 専門家ぶった口調や、読者を見下す表現がないか
- [ ] 冗長な節はないか（学習の流れに必要ない情報は削る）
- [ ] **この記事にしかない一次情報（実際に試した結果）が最低1つ入っているか**。出力・数値はユーザー本人が実行したものか（作っていないか）
- [ ] **1記事1テーマか**。持ち帰ることを一文で言えるか。本文が約10,000字を超えていないか
- [ ] **タイトルは全角40文字以内で、読者の得が見えるか**
- [ ] **たとえ話（擬似語）が入っているか**：「先に結論」にたとえの小節があり、世界観が1つに統一され、技術用語との対応表があり、たとえが当てはまらない点が書かれているか。たとえで新しい事実を断定していないか

### 公開前チェック（`published: true` にする前に必ず）

- [ ] 本文・HTMLコメントに `TODO` / 仮置き / 未確認 の記述が残っていない（`grep -n "TODO" 対象ファイル` で確認する）
- [ ] 仮置きの体験談（「正直ピンときませんでした」など）が、本人の実体験に差し替わっている
- [ ] 公式ドキュメントで裏取りできていない記述を、事実として書いていない（確認できなければ削除する）
- [ ] mermaid など Qiita のプレビューで表示崩れがないか（ラベル内の改行は `<br/>` を使う）

1つでも残っていれば `published: false` のままにして、残件をユーザーに伝える。**TODO を残したまま `published: true` にしない。**

## Qiita 向けの取り決め

このリポジトリは `qiita/articles/*.md` を GitHub Actions で Qiita に自動投稿する（詳細は README.md）。

- front matter は `title` / `tags` / `published` / `private` / `coediting` / `tweet` を指定する。
- **新規記事・書き直しの下書きは `published: false` で作る**。`true` で `main` に push すると即公開されるため、公開はユーザーが決める。上記「公開前チェック」をすべて満たすまで `true` にしない。
- 返答の最後に、**ユーザーが対応すべき残件**（実験の実行と出力の貼り付け、実体験への差し替え、タイトル選択など）を一覧で伝える。
- 既存記事を上書きせず、別ファイルで書いて比較できるようにする（ユーザーから上書きを頼まれた場合を除く）。
- ファイル名は内容がわかる英小文字・ハイフン区切り（例：`rds-vs-bigquery-learning.md`）。
- 1記事のタグは関連するものを5個以内にする。

## 既存記事を「学習者目線」に書き直す場合

1. 元の記事の**技術的な内容は維持**し、誤りがあれば指摘する（黙って変えない）。
2. 専門家口調の説明を、「疑問 → 調べた → 理解した」の流れに組み替える。
3. 元の記事の冒頭の疑問リストは、「わからなかったこと」の見出しに対応させる。
4. 網羅性より「つまずきの解消」を優先し、学習の流れに関係の薄い細部は削るか短くする。
5. 返答では、どの箇所をどう変えたか、**ユーザーの実体験で差し替えるべき箇所**を最後に伝える。
