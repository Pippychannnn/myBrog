# 学習者目線の技術記事を書くスキル

「専門家が教える」記事ではなく、**「自分はここがわからなかった。調べたらこう理解できた」を共有する記事**を書く。
読者は過去の自分と同じところでつまずいている人。その人が「自分も同じところで悩んでいた」と感じ、読み終えて腑に落ちることをゴールにする。

## 大原則

1. **つまずきを主役にする**：「何を知っているか」ではなく「どこでわからなくなったか」を軸に構成する。
2. **経験を捏造しない**：実際のつまずき、失敗談、課金額、試した結果などは、ユーザー本人が語ったものだけを書く。わからない場合は書かずに質問する（後述の「ヒアリング」）。
3. **断定しすぎない**：調べて理解した立場なので、確認できたことと、そう理解したこと・未確認のことを区別して書く。
4. **正確さは落とさない**：親しみやすい文体にしても、技術的な内容は公式ドキュメントで裏取りする。

## 進め方

### 1. ヒアリング（書く前に確認する）

次を確認する。ユーザーがすでに文章や下書きを渡している場合は、そこから読み取れるものは聞き直さない。

- どこでつまずいたか（疑問・誤解していたこと）
- どう調べて、何がきっかけで腑に落ちたか
- まだわかっていないこと、試せていないこと
- 想定読者（例：Webエンジニア、初学者など）

つまずきが不明で、本文の疑問から推測して書く場合は、**推測で入れた箇所を最後にユーザーへ明示して、本人の実体験に差し替えてもらう**。

### 2. 構成を作る

以下の型を基本にする。内容に合わせて増減してよい。

```
タイトル：「〇〇がわからなかったので、△△から調べて整理した」型
# はじめに
  - なぜ調べたか（きっかけ）
  - わからなかったことのリスト（3〜5個）
  - 立場の表明（専門家ではなく、調べた範囲での共有。誤りはご指摘ください）
# 先に結論（3行 or 比較表）
# わからなかったこと①〜⑤
  - 何がわからなかったか（素直に）
  - 調べてどう理解したか
  - 具体例・図・コード
# まだ腑に落ちていないこと
# まとめ（箇条書き＋最後の一言）
```

ポイント：
- 先に結論を置き、読者が全体像を持ってから詳細を読めるようにする。
- 各節の見出しは「わからなかったこと」の形にして、疑問と答えを対応させる。
- 前の節で出た概念が次の節の疑問を解く、という**つながり**を明示する（例：「①がわかると、これも説明できる」）。
- 疑問は「はじめに」で列挙し、まとめで回収する。

### 3. 書く

**文体**
- です・ます調。一人称は「自分」「筆者」。偉そうな言い回し（「〜すべき」「当然」）を避ける。
- つまずきは素直に書く。例：「正直、この説明だけでは何が違うのかピンときませんでした」「最初は〜だと思っていました」
- 理解の転換点を書く。例：「ここで〇〇とつながって、やっと腑に落ちました」
- 「簡単に」「単純に」「ご存じの通り」など、読者を置き去りにする言葉は使わない。

**わかりやすさ**
- 略語・専門用語は、初出で正式名称と**自分の言葉での言い換え**を添える。
- 抽象的な説明の直後に、小さな具体例（小さな表、数行のSQL/コード）を置く。
- 比較は表にする。流れや構成は mermaid 図にする（Qiita は mermaid 対応）。
- 1つの節で扱う概念は1つ。長くなる場合は節を分ける。
- 「意外だったこと」「誤解しやすいこと」は `:::note info` / `:::note warn` で目立たせる。

**正確さ**
- 「必ず」「常に」「できない」の断定を疑う。例外・条件がある場合は書き添える。
- 製品・サービスの仕様、料金、制限は変わりうるので、公式ドキュメントを確認し、前提（課金モデル、バージョンなど）を明記する。
- 確認できていないことは「〜と理解しています」「〜のようです」とし、裏取りできていない内容を事実として書かない。

### 4. セルフチェック

仕上げる前に確認する。

- [ ] 「はじめに」で挙げた疑問は、すべて本文で答えが出ているか
- [ ] つまずきの記述は、ユーザー本人の実体験か（捏造していないか）
- [ ] 初出の用語に言い換えがあるか
- [ ] 断定表現に、例外・前提が添えられているか
- [ ] 「まだわかっていないこと」を正直に書いているか
- [ ] 専門家ぶった口調や、読者を見下す表現がないか
- [ ] 冗長な節はないか（学習の流れに必要ない情報は削る）

## Qiita 向けの取り決め

このリポジトリは `qiita/articles/*.md` を GitHub Actions で Qiita に自動投稿する（詳細は README.md）。

- front matter は `title` / `tags` / `published` / `private` / `coediting` / `tweet` を指定する。
- **新規記事・書き直しの下書きは `published: false` で作る**。`true` で `main` に push すると即公開されるため、公開はユーザーが決める。
- 既存記事を上書きせず、別ファイルで書いて比較できるようにする（ユーザーから上書きを頼まれた場合を除く）。
- ファイル名は内容がわかる英小文字・ハイフン区切り（例：`rds-vs-bigquery-learning.md`）。
- 1記事のタグは関連するものを5個以内にする。

## 既存記事を「学習者目線」に書き直す場合

1. 元の記事の**技術的な内容は維持**し、誤りがあれば指摘する（黙って変えない）。
2. 専門家口調の説明を、「疑問 → 調べた → 理解した」の流れに組み替える。
3. 元の記事の冒頭の疑問リストは、「わからなかったこと」の見出しに対応させる。
4. 網羅性より「つまずきの解消」を優先し、学習の流れに関係の薄い細部は削るか短くする。
5. 返答では、どの箇所をどう変えたか、**ユーザーの実体験で差し替えるべき箇所**を最後に伝える。
